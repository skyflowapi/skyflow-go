# Skyflow Go SDK — Claude Code Instructions

## Project Overview

This is the Skyflow Go SDK (`skyflow-go`). It provides a Go interface to the Skyflow Data Privacy Vault API — vault operations (insert, get, update, delete, query, tokenize, detokenize), service account authentication (bearer tokens, signed data tokens), connections, detect, and audit.

**v1 (maintenance mode, root package):** Security and bug fixes only — no new features. EOL announced: **October 31, 2026**.

**Current stable version: v2.1** — supports PDB vaults. Module path: `github.com/skyflowapi/skyflow-go/v2`. This is what customers use.

## Critical Boundary — Generated Code

**Never edit files under `v2/internal/generated/`.**

These are auto-generated by [Fern](https://buildwithfern.com) from the Skyflow API definition. Manual edits are overwritten on the next generation run. If you find a bug in generated code, report it — do not patch it directly.

`v2/.golangci.yml` already excludes `internal/generated` and `test` from lint checks.

## Naming Conventions

These intentionally deviate from standard Go convention for cross-SDK consistency (Java parity):

- **`Id` suffix (not `ID`):** `VaultId`, `ClusterId`, `SkyflowId`, `ConnectionId`, `RequestId` — never `VaultID`
- **`Url` suffix (not `URL`):** `DownloadUrl`, `BaseVaultUrl` — never `DownloadURL`
- **`Api` prefix (not `API`):** `ApiKey` — never `APIKey`
- The `revive` linter allows these via its `var-naming` allowlist in `v2/.golangci.yml`. Add `//revive:disable-next-line:var-naming` only for outliers not covered by the allowlist.
- **Messages:** All log and error message strings live in `v2/utils/messages/` — no inline string literals in code
- **Constants:** SDK-internal constants live in `v2/internal/constants/constants.go`; error code strings live in `v2/utils/error/error_codes.go`

## SDK Coding Rules

These apply whenever writing or modifying code — not just during review.

### Error handling
- All public methods must return `*skyflowError.SkyflowError` as the error type — never raw `error`
- Never swallow errors — always return them to the caller
- No `fmt.Println`, `log.Print*`, or `panic` in SDK code — use `logger.Error/Info/Warn` from `v2/utils/logger`
- Always call `logger.Error(...)` before returning a `SkyflowError`

### Message and constant strings
- All error and log messages must be constants in `v2/utils/messages/` (e.g. `logs.EMPTY_TABLE`) — no magic strings inline
- All SDK-internal string constants go in `v2/internal/constants/constants.go`
- `goconst` linter will flag repeated string literals — fix them by adding a constant

### Request / Response patterns
- Request structs are data holders — all validation belongs in `v2/internal/validation/ValidateXxxRequest()`
- Options structs carry per-call settings (custom headers, redaction type, etc.) — keep them separate from request structs
- All response structs must have an `Errors` field (slice, nil when no errors)

### Context
- All public API methods must accept `context.Context` as their first parameter

### Tests
- Test framework: **Ginkgo v2 + Gomega** — use `Describe` / `It` / `Expect` blocks
- All code written or modified must have 100% coverage — both statement and branch
- No mocking of the production struct under test; use interface substitution or function-variable injection (e.g. `CreateDetectRequestClientFunc`)

## Build and Test

All commands run from `v2/` or the project root with explicit paths:

```bash
# Compile
go build ./v2/...

# Lint (golangci-lint with revive + goconst, config: v2/.golangci.yml)
cd v2 && golangci-lint run

# Full test suite
cd v2 && go test ./...

# Single test suite (by Ginkgo suite name or -run pattern)
cd v2 && go test ./internal/validation/... -v
cd v2 && go test ./... -run "TestName"

# Coverage report
cd v2 && go test ./... -coverprofile=coverage.out && go tool cover -func=coverage.out

# Dependency hygiene
cd v2 && go mod tidy
```

## Credentials JSON Format

The SDK reads a credentials JSON file for service account authentication:

```json
{
  "clientID": "...",
  "keyID": "...",
  "tokenURI": "...",
  "privateKey": "..."
}
```

## Slash Commands

- `/code-review` — full review: Go patterns + code smells + security
- `/code-smell` — standalone structural smell analysis only (long functions, dead code, magic numbers)
- `/code-security` — standalone security audit only (credentials, input validation, HTTP security)
- `/sdk-sample <feature>` — generate a sample file for a feature
- `/code-quality [./path/...]` — run quality pipeline (build → lint → test → coverage check)
- `/git-commit <description>` — stage check + Jira-aware commit (extracts ticket ID from branch name)

## Commit & PR Guidelines

### Commit messages
**Never run `git commit` directly. Always use `/git-commit <description>`** — it extracts the Jira ticket ID from the branch name, confirms `/code-quality` has passed, and validates the format against the CI check in `.github/workflows/main.yml`.

### Branch naming
Branch name must include your GitHub username:

```
<github-username>/<ticket-id>-<short-description>
```

Example: `devesh/SK-770-ext-auth-json-error`

### PR template
`.github/workflows/pull_request_template.md` requires: **Why**, **Goal**, **Testing** sections. Tech debt section is optional.
